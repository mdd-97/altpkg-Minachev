## 1. Командная оболочка

| Команды | Класс | Пакет |
|---|---|---|
| read, printf | Встроенные команды Bash | bash |
| ll | Псевдоним ls -l, заданный для опыта | — |
| rpm, sed, grep | Внешние программы | rpm, sed, grep |

Команда type -a показывает возможные способы разрешения имени. Например, у printf также есть внешний вариант, но в Bash сначала выбирается встроенная команда. Владельцев внешних файлов проверил rpm -qf. Дочерняя оболочка получила LAB04_VALUE только после export. Изменение в дочернем процессе не изменило переменную родителя.

| Подстановка для one/two/three | Вывод |
|---|---|
| ${V#*/} | two/three |
| ${V##*/} | three |
| ${V%/*} | one/two |
| ${V%%/*} | one |

Перенаправления применяются слева направо. В `> combined 2>&1` stderr копирует уже перенаправленный stdout. В `2>&1 > stdout-only` stderr остаётся на прежней цели stdout. Без номера дескриптора `>` меняет только stdout. diff вернул 1 при сравнении файлов. Цикл читает имя назначения из встроенного документа и проверяет конвейер uname, head, cut, tr. Результат linux совпал с эталоном. Журнал — task01.log.

## 2. Временные файлы

mktemp выдаёт разные имена и создаёт файл с режимом 600. Каталог создаётся с 700: чтение и изменение доступны владельцу, для входа в каталог требуется бит исполнения. trap EXIT удаляет файл, обработчики INT и TERM завершают сценарий кодами 130 и 143. Наблюдающий процесс подтвердил существование файла до отправки сигналов и отсутствие после. Штатный код 0, предусмотренный аварийный код 7. mktemp -u печатает имя без резервирования, поэтому это только опыт. Три X приняты, два X отклонены с диагностикой. Журнал — task02.log.

## 3. Текстовые данные

Из одного снимка `ps -eo pid=,comm=,user=` подготовил два файла с общим ключом PID. После сортировки и join в LC_ALL=C у каждой исходной строки есть строка результата. cut, tr, head и tail выделяют поля и меняют регистр. Для опыта с локалью использовал два ключа Z и a, порядок которых различается. join --check-order в ru_RU.utf8 отверг вход, предварительно отсортированный в C. При одинаковой локали C получены обе строки. Журналы — task03.log и task03-locale.log.

Фрагмент ALT с переводом строки имеет байты 41 4c 54 0a. hexdump из util-linux, od из coreutils и xxd из одноимённого пакета показали те же значения. Прямое перенаправление в исходный файл обрезает его до чтения, sponge ждёт завершения входного потока. ts добавляет отметку времени. Журнал — task03-moreutils.log.

## 4. Список задач

Сценарий rdsu-tasks хранит TSV в `$XDG_CONFIG_HOME/rdsu-tasks` или в `~/.config/rdsu-tasks`. touch создаёт файл при первом запуске и сохраняет существующее содержимое при повторном. Режимы add, done и list работают без dialog. Экранное меню получает выбор из stderr во временный файл. Массив аргументов Bash и подстановка "${array[@]}" передают каждый ID и текст целыми аргументами, включая пробелы. EXIT удаляет временные файлы. Три записи добавлены, одна отмечена. diff с tasks.expected завершился с кодом 0. В псевдотерминале заголовок RDSU Tasks подтверждён, выход вернул код 0, временный файл удалён. Журналы — task04-cli.log, task04-menu.log и протокол меню.

## 5. RPM

SPEC использует исходный сценарий напрямую и устанавливает его в %_bindir с режимом 755. BuildRequires и явных Requires нет. Автоматический разбор строки интерпретатора и команд дал /bin/bash, coreutils, dialog, gawk, grep и sed. FINDPACKAGE-COMMANDS перечислил awk, dialog, grep, mkdir, mktemp, mv, rm, sed и touch. Установка без dialog отвергнута, после установки зависимости пакет установлен и запущен по имени в Hasher. Журналы — task05-build.log и task05-runtime.log.

## 6. GEAR

gear-srpmimport создал master, srpms и тег 1.0-alt1. В дереве находятся открытый сценарий, SPEC и .gear/rules. Правило `copy: rdsu-tasks` экспортирует сценарий как отдельный файл для Source0. Сборка gear-rpm на основном стенде не включила dialog в Requires: сборщик сопоставлял команду с пакетами текущего окружения. При повторной сборке из GEAR в Hasher совпали имя, версия, релиз, список файлов и зависимости: все три сравнения diff дали код 0. Журналы — task06-import.log, task06-gear-build.log и task06-gear-hasher.log.

## Вывод

Оболочка связывает системные команды и запускает тесты с проверкой их кодов. Экранный интерфейс и неинтерактивный режим одного приложения используют одно хранилище. RPM вычисляет зависимости сценария, а GEAR воспроизводит сборку по тегу.
