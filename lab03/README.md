# ЛР3. Многофайловая сборка

Миначев Дамир. Стенд `rdsu-alt`, ALT Platform Builder 11.0, p11, x86_64. Работа начата в свежем клоне ветки `dev` с коммита `0721e6b`. Команды, вывод и диагностика сохранены в `logs/`.

## 1. Модули и этапы сборки

`main.c` задаёт порядок работы, `output.c` печатает параметры и справку, `counter.c` выделяет память под счётчик. `args.h` содержит объявления и версию. При вызове без параметров справка идёт в stderr, stdout остаётся пустым, код возврата 0. Три параметра дают пять строк с метками BEGIN и END.

Препроцессор разворачивает включения и макросы. `cc -E` даёт текст с объявлением `print_arg`. Компиляция переводит текст в ассемблерный код, ассемблер формирует перемещаемые `.o`, компоновщик разрешает ссылки и получает исполняемый файл. В трассировке видны `cc1`, `as`, `collect2` и `ld`. Если поместить определение `duplicate` в общий заголовок, каждый модуль создаёт одноимённый глобальный символ. `ld` завершает сборку ошибкой повторного определения, код 1. [Журнал](logs/task01.log)

## 2. Символы

В `nm` тип T означает функцию в секции кода, B означает неинициализированные данные, D означает инициализированные данные, U означает ссылку на символ из другого объекта или библиотеки. Глобальных символов D в исходных модулях нет.

| Символ | Тип | Определение | Использование | Источник |
|---|---|---|---|---|
| `main` | T | `main.o` | стартовый код C | [nm и ldd](logs/task02.log) |
| `counter` | B | `counter.o` | `main.o`, `output.o` | [nm](logs/task02.log) |
| `print_arg` | T | `output.o` | `main.o` | [nm](logs/task02.log) |
| `print_help` | T | `output.o` | `main.o` | [nm](logs/task02.log) |
| `puts` | U в проекте | libc | `main.o` | [nm и comm](logs/task02.log) |
| `printf`, `fwrite`, `stderr` | U в проекте | libc | `output.o` | [nm и comm](logs/task02.log) |

`comm -23` вычитает из отсортированных неопределённых имён определения проекта. Повторное вычитание экспортов libc даёт пустой список. `ldd` показывает libc, загрузчик и виртуальную библиотеку ядра.

## 3. Make

Make строит зависимости из целей и их реквизитов, затем сравнивает время изменения файлов. Явные рецепты и шаблон `%.o: %.c` дали одинаковые команды. Встроенное правило использует `COMPILE.c`, `OUTPUT_OPTION` и исходник. В рецептах `$@` — цель, `$<` — первый реквизит, `$^` — все реквизиты без повторов.

После `touch main.c` выполнены одна компиляция и одна компоновка. До добавления `args.h` изменение заголовка не вызвало пересборку. После добавления зависимости пересобрались три модуля, а переданное `CFLAGS=-O0` изменило команды. `.PHONY` позволяет выполнить очистку даже при наличии файла `clean`. [Журнал](logs/task03.log)

## 4. Статическая библиотека

Архив `librdsuargs.a` содержит `output.o` и `counter.o`. Встроенное правило make добавляет объектные файлы в архив. `.SECONDARY` сохраняет промежуточные объекты. `cmp` подтвердил совпадение вывода с прямой компоновкой.

Флаг `-static` требует статическую libc. На стенде без `glibc-devel-static` компоновщик завершился с `cannot find -lc` и кодом 1. [Журнал](logs/task04.log)

Пакет установлен в Hasher. Полная компоновка и сравнение вывода завершились с кодом 0. Размеры, число символов и вывод ldd приведены в таблице ниже. [Журнал](logs/task04-static-hasher.log)

| Вариант | Байт | Символов | ldd |
|---|---:|---:|---|
| Архив проекта и динамическая libc | 18808 | 36 | libc и загрузчик разрешены |
| Полностью статический | 3044320 | 1930 | not a dynamic executable |


## 5. Динамическая библиотека

PIC — код, рассчитанный на загрузку по разным адресам. Без `-fPIC` компоновщик отклонил перемещение `R_X86_64_32`, код 1. С `-fPIC -shared` получена `librdsuargs.so` с двумя функциями и счётчиком. Статическая библиотека встраивает нужные объекты в программу, динамическая остаётся отдельным файлом и загружается при запуске.

Без указания каталога загрузчик выдал `cannot open shared object file`, код 127. Для имени без косой черты загрузчик учитывает RPATH при отсутствии RUNPATH, затем `LD_LIBRARY_PATH`, RUNPATH, кэш и стандартные каталоги. Установка `LD_LIBRARY_PATH` только для процесса разрешила все зависимости. Вывод совпал со статическим вариантом. [Журнал](logs/task05.log)

## 6. Функциональная проверка Make

Три варианта программы запущены без параметров, с одним и с тремя параметрами. Оба потока каждого запуска сведены в один из девяти файлов. Справка использует постоянное имя программы. Попарный `cmp` подтвердил совпадение выводов. После изменения формата и пересборки одного варианта `make test` завершился с кодом 2. После восстановления проверка вернула 0. `make distclean` оставил три исходника, заголовок и Makefile. [Журнал](logs/task06.log)

## 7. RPM

Hasher создаёт отдельный корень файловой системы для сборки. `env/build-rpm.sh` создаёт архив `rdsu-args-1.0.tar.gz`, исходный RPM и запускает Hasher. В SPEC каталог команд задан через `%_bindir` (на стенде `/usr/bin`), каталог библиотеки через `%_libdir` (`/usr/lib64` для x86_64). Макросы RPM учитывают платформу при сборке. Исходный RPM содержит исходники и рецепт. Подпакет `rdsu-args-debuginfo` содержит данные для отладки.

Основной RPM предоставляет `librdsuargs.so()(64bit)`. На этой версии ALT RPM удалил из итогового Requires зависимость, которую основной пакет уже предоставляет сам. Зависимость динамического исполняемого файла видна как ELF-запись `NEEDED`, а статический вариант использует библиотеку проекта из архива и сохраняет зависимость от динамической libc. [Сборка](logs/task07-build.log)

После установки оба файла запущены по имени без LD_LIBRARY_PATH. Сравнение cmp завершилось успешно. ldd разрешил librdsuargs.so из стандартного каталога, а rpm -qf подтвердил принадлежность файла основному пакету. [Установка и проверка](logs/task07-runtime.log)

## 8. Сценарий проверки

```sh
bash -n lab03/check/check-lab03.sh
lab03/check/check-lab03.sh
LAB03_HASHER_WORKDIR="$HOME/rdsu-lab03/rpm/hasher" lab03/check/check-lab03.sh
```

Сценарий компилирует варианты во временном каталоге, сравнивает выводы с эталонами и проверяет журналы опытов. Группа Hasher выполняется при наличии подготовленной среды. Итоговые счётчики — PASS, FAIL, SKIP. Любой FAIL даёт ненулевой код.

На стенде с Hasher получено PASS=26 FAIL=0 SKIP=0. Для приёмочной проверки нужен свежий клон ветки dev с тегом lab03. Повреждение проверяется в отдельном клоне заменой строки эталона, после опыта исходный эталон восстанавливается через Git.


## Вывод

Лабораторные опыты показали, как make пересобирает изменившиеся зависимости и как выбор способа компоновки меняет требования к установленной программе. Для варианта с динамической библиотекой RPM размещает её в стандартном каталоге архитектуры, чтобы загрузчик мог найти её без переменных окружения. Приёмка преподавателем ожидается.
