## Задание 3. Пакеты libinih0 и libinih-devel

Состав пакетов:

| Категория | libinih0 | libinih-devel |
|---|---|---|
| Разделяемые библиотеки | `libinih.so.0`, `libINIReader.so.0` | — |
| Заголовочные файлы | — | `ini.h`, `INIReader.h` |
| Символические ссылки на .so | — | `libinih.so`, `libINIReader.so` |
| Описания для компоновки (pkg-config) | — | `inih.pc`, `INIReader.pc` |
| Документация | `README.md`, `LICENSE.txt` | — |

Ссылка `libinih.so` нужна только компоновщику при сборке (`-linih`), работающей программе нужен файл с soname `libinih.so.0`.
`rpm -qf /usr/include/INIReader.h` возвращает `libinih-devel`; `rpm -q --whatprovides libinih0` возвращает `libinih0`.
Пакет `libinih0` был установлен до начала работы: его требует `xfsprogs` через soname `libinih.so.0()(64bit)`.

## Задание 4. Изолированное окружение

Конфигурация: сопровождающий `Damir Minachev <mdd97@yandex.ru>`; отключены проверки `gpg` (пакеты не подписываются),
`packager` и `changelog` (сопровождающий и автор записи changelog не зарегистрированы в репозитории ALT).
Права на файлы источников APT (`-rw-r--r--`) позволяют чтение группе `hashman`, исправление не потребовалось.

| Роль | Хост-пользователь (UID) | hasher-priv | Имя в окружении | `id -un` | Домашний каталог |
|---|---|---|---|---|---|
| Служебный суперпользователь | user_a (1001) | user1 | rooter | root | /root |
| Сборщик | user_b (1002) | user2 | builder | builder | /usr/src |

Соответствие подтверждено `/etc/hasher-priv/user.d/1000` и владельцем `/usr/src/RPM` (UID 1002).
Rooter работает с эмулированным UID 0, поэтому `id -un` выводит `root`; реальных прав root в хост-системе у него нет.

## Задание 6. Вычисленные зависимости пакета altpkg-minachev-1.0-alt2

Этапы журнала сборки: очистка (`rm -rf` buildroot), установка файлов (`install -D`), проверка дисциплины сборки (`brp-alt`),
вычисление зависимостей (`find-provides`, `find-requires`), запись пакетов (`Wrote:`).

| Зависимость | Тип | Происхождение |
|---|---|---|
| `/bin/sh` | требуемая | вычислена анализаторами `shebang`/`shell` по строке `#!/bin/sh`; `echo` — встроенная команда оболочки |
| `rpmlib(PayloadIsLzma)` | требуемая | анализатор `rpmlib`: содержимое пакета сжато LZMA, нужен rpm с поддержкой этого формата |
| `altpkg-minachev = 1.0-alt2` | предоставляемая | rpm добавляет имя пакета с версией-релизом автоматически |

Ни одна зависимость в spec-файле явно не объявлена.

## Задание 7. Воспроизводимость и состав окружений

Автоматическая сборка `hsh` из `src.rpm` дала пакет с тем же именем, версией, релизом, перечнем файлов и зависимостей;
`sha256sum` исходного файла из обоих пакетов и из репозитория совпадает. Сами файлы `.rpm` различаются из-за времени сборки
в метаданных — воспроизводимость подтверждена на уровне содержимого и метаданных.

Первая автоматическая сборка была отклонена проверкой `sisyphus_check` (`check-changelog`): автор записи changelog не
зарегистрирован в ALT. `rpmbuild` такую проверку не выполняет, `hsh` выполняет; проверка отключена в конфигурации.

Пакетов на хосте 956, в окружении 180. Только на хосте — 786: инструментальные (`hasher`, `rpmdevtools`, `git-core`,
`mc`, `tree`, `openssh-clients`) и эксплуатационные пакеты рабочей системы. Окружение содержит лишь базовую систему,
средства сборки и их эксплуатационные зависимости. Из 10 пакетов «только в окружении» 9 — те же пакеты в более новых
версиях из p11, один (`branding-xalt-kworkstation-release`) — другой поставщик release-файла вместо
`branding-alt-platform-builder-release` хоста.

## Задание 8. Проверка

`bash lab01/check/check-lab01.sh` выполняет 30 проверок заданий 2–7, печатает PASS/FAIL и итог, при любом FAIL
завершается с кодом 1. Чувствительность: при порче `check/expected.txt` проверка 6.4 даёт FAIL (24/1, код 1),
после восстановления — 25/0 (на момент проверки, до добавления заданий 3), код 0.

## Выводы

1. Зависимости делятся на инструментальные (средства разработчика), сборочные (нужны для компиляции) и
   эксплуатационные (нужны при работе программы); они определяются средствами rpm и apt.
2. Эксплуатационные зависимости пакета не объявляются вручную, а вычисляются при сборке по содержимому файлов.
3. Библиотека разделена на основной пакет (soname, нужен для работы) и devel-пакет (заголовки, ссылки .so, .pc — нужны для сборки).
4. Сборка в hasher выполняется без прав суперпользователя в пересоздаваемом окружении с минимальным набором пакетов,
   поэтому её результат не зависит от состояния машины разработчика и воспроизводим.
